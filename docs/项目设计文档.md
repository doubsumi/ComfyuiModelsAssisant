# Part 1 · 项目设计文档

## 1. 项目概述

### 1.1 背景

用户以 ComfyUI 为主要生产工具制作国漫短片，已下载并跑通多个架构的模型（Krea2、Boogu、MiniMax H3 系列），同时拥有 SD WebUI 环境。当前痛点：

1. **模型知识分散**：哪些模型能互相搭配、哪个 LoRA 配哪个底模，全靠记忆和社区经验。
2. **探索成本高**：想尝试新组合（比如给 MiniMax H3 挂一个从未用过的 LoRA）需要手动改工作流，试错慢。
3. **模型文件价值未充分利用**：下载成本高（时间 + 空间），但用起来的可能只有几个固定组合。
4. **注册表无法自动维护**：ComfyUI 官方接口只能列出文件，不能提供架构和兼容性信息。

### 1.2 核心目标

构建一个**本地运行的模型组合探索与工作流生成系统**，让用户能够：

1. 看到所有已下载模型的**架构、角色、兼容关系**
2. **勾选任意模型文件**，得到即时的兼容性反馈和推荐组合
3. 从任意兼容组合**一键生成可加载的 ComfyUI 工作流 JSON**
4. 通过 **LLM Patch 机制**持续补充模型知识库
5. 保存常用组合为**预设**，下次一键复用

### 1.3 非目标（明确不做）

| 不做          | 理由                        |
| ----------- | ------------------------- |
| SD WebUI 集成 | 第一版只做 ComfyUI             |
| 云端部署 / 多用户  | 本地单用户工具                   |
| 模型训练 / 微调   | 只做推理侧的组合                  |
| 自动下载模型      | 用户自行管理下载                  |
| LLM 本地部署    | 用外部 LLM 生成 Patch，不引入本地推理  |
| 工作流自动执行     | 只生成 JSON，由用户在 ComfyUI 里运行 |

### 1.4 成功标准

- 用户能在 3 次点击内从「想试一个新组合」到「拿到可运行的工作流 JSON」
- 模型注册表覆盖率 ≥ 95%（已下载的模型都能被识别架构）
- Patch 从生成提示词到合并入库，全程 ≤ 5 分钟
- 兼容性判断零误报（宁可漏报也不误报）

## 2. 用户故事

### US-1：快速确认组合可行性

> 作为用户，我想勾选 Krea2 主模型 + 一个不认识的 LoRA，系统立即告诉我这个 LoRA 是否兼容，避免我去 ComfyUI 里试错。

### US-2：探索新组合

> 作为用户，我想先勾选一个主模型，系统告诉我还差哪些配套模型，我不用记住"Krea2 需要 qwen3vl\_4b 编码器"这类细节。

### US-3：从组合到工作流

> 作为用户，选好模型组合后，我想直接下载一份可以在 ComfyUI 里加载的工作流 JSON，不用手动搭节点。

### US-4：批量补充模型知识

> 作为用户，我新下载了一批模型，我想让 LLM 一次性生成它们的架构信息，通过 Patch 机制批量入库。

### US-5：保存常用配置

> 作为用户，我把"国漫短片主力配置"保存为预设，下次打开就能一键加载。

### US-6：提示词快速起步

> 作为用户，我不想从零写提示词，系统给每个架构一套国漫向模板，直接填入工作流。

## 3. 功能需求

### 3.1 模块划分

系统分为 6 个模块，按依赖关系从底向上排列：

```
M6: 提示词助手          ← 独立功能
M5: 预设与收藏          ← 依赖 M2、M4
M4: 工作流生成器        ← 依赖 M2、M3
M3: 组合推荐引擎        ← 依赖 M2
M2: 模型注册表          ← 依赖 M1
M1: 模型文件管理        ← 基础层
```

### 3.2 M1 · 模型文件管理

**职责**：扫描 ComfyUI 模型目录，提供文件清单。

**功能点**：

| 编号    | 功能    | 说明                                     |
| ----- | ----- | -------------------------------------- |
| M1-F1 | 目录扫描  | 递归扫描 models 目录，过滤支持的文件扩展名              |
| M1-F2 | 分类展示  | 按子目录（diffusion\_models/loras/vae...）分组 |
| M1-F3 | 搜索过滤  | 按文件名、备注、分类过滤                           |
| M1-F4 | 用户备注  | 用户可对任意文件填写自定义备注，持久化                    |
| M1-F5 | 打开文件夹 | 点击路径调用系统资源管理器                          |

**非功能点**：

- 扫描 1000 个文件 ≤ 3 秒
- 备注不因重新扫描丢失

### 3.3 M2 · 模型注册表

**职责**：为每个模型文件建立结构化的元数据档案。

**功能点**：

| 编号    | 功能       | 说明                                |
| ----- | -------- | --------------------------------- |
| M2-F1 | 架构识别     | 识别模型的架构（FLUX/Krea2/MiniMax H3...） |
| M2-F2 | 角色识别     | 识别模型角色（unet/encoder/vae/lora...）  |
| M2-F3 | 兼容性推导    | 推导模型间的兼容关系                        |
| M2-F4 | 三层识别策略   | 元数据 → 启发式 → LLM Patch             |
| M2-F5 | Patch 更新 | 通过 LLM 生成的 Patch 增量更新             |
| M2-F6 | 版本管理     | 注册表版本化，Patch 需匹配版本                |
| M2-F7 | 校验机制     | Patch 格式、字段、架构白名单校验               |

**三层识别策略**：

| 层级       | 数据来源                       | 覆盖率预估 | 置信度      |
| -------- | -------------------------- | ----- | -------- |
| Layer 1a | safetensors `__metadata__` | \~50% | 0.9      |
| Layer 1b | tensor 名称启发式               | +20%  | 0.6-0.95 |
| Layer 3  | LLM Patch                  | 兜底    | 1.0      |

**非功能点**：

- Patch 校验需在 500ms 内完成
- 校验失败必须返回可读的错误列表
- 注册表支持并发读（写入串行化）

### 3.4 M3 · 组合推荐引擎

**职责**：用户勾选任意模型后，给出兼容性报告和推荐方案。

**功能点**：

| 编号    | 功能        | 说明                          |
| ----- | --------- | --------------------------- |
| M3-F1 | 实时兼容检查    | 用户勾选变化时立即校验                 |
| M3-F2 | 缺失配套提示    | 选了 unet 但没选 encoder/vae 时提示 |
| M3-F3 | 冲突诊断      | 明确指出为什么不兼容，给出替代方案           |
| M3-F4 | 多主模型冲突处理  | 勾选多个 unet 时要求用户选择           |
| M3-F5 | LoRA 权重建议 | 根据 LoRA 元数据给出推荐权重           |

**兼容性判定规则**：

1. unet 的 `arch` 决定可用 encoder、vae 的白名单
2. LoRA 的 `arch` 必须与 unet 的 `arch` 匹配
3. encoder 的 `encoderNodeParams` 必须与 unet 要求一致
4. 多个 LoRA 之间无冲突（同名或同权重区间）

### 3.5 M4 · 工作流生成器

**职责**：从兼容的模型组合生成完整的 ComfyUI 工作流 JSON。

**功能点**：

| 编号    | 功能        | 说明                                            |
| ----- | --------- | --------------------------------------------- |
| M4-F1 | 图谱模式实例化   | 从架构对应的图谱模式生成节点                                |
| M4-F2 | LoRA 动态插入 | 按用户选择的 LoRA 数量动态生成节点                          |
| M4-F3 | 参数注入      | 将用户参数写入对应节点的 widgets\_values                  |
| M4-F4 | 提示词注入     | 将提示词写入 CLIPTextEncode / MiniMaxH3ImageToVideo |
| M4-F5 | 可选输入处理    | 图生视频的 first/last frame 按需保留                   |
| M4-F6 | JSON 预览   | 生成前可预览                                        |
| M4-F7 | 下载 / 保存   | 下载到本地 / 保存到 ComfyUI workflows 目录              |
| M4-F8 | 插件依赖提示    | JSON 内嵌插件依赖，页面展示                              |

**核心设计原则**：

**工作流生成必须与具体工作流文件解耦。**

用户已经明确指出：「不要被现有工作流局限」。因此生成器不能基于「模板 JSON 填充」的方案，而必须基于 **图谱模式（Graph Pattern）**——一种抽象的节点图描述，与具体工作流文件无关。

图谱模式的抽象层级：

```
GraphPattern (每种架构一个)
  ├── nodes[]              # 节点类型 + widgets 定义
  ├── connections[]        # 静态连接关系
  ├── loraInsertionPoint   # LoRA 动态插入位置
  └── optionalNodes[]      # 可选节点（如图片输入）
```

实例化流程：

```
GraphPattern + 用户选择 → 节点实例化 → 参数注入 → links 构建 → JSON 序列化
```

### 3.6 M5 · 预设与收藏

**职责**：保存常用的模型组合。

**功能点**：

| 编号    | 功能   | 说明                        |
| ----- | ---- | ------------------------- |
| M5-F1 | 保存预设 | 命名 + 保存当前的模型选择、LoRA 权重、参数 |
| M5-F2 | 加载预设 | 一键恢复所有选择                  |
| M5-F3 | 预设列表 | 展示所有预设，支持搜索               |
| M5-F4 | 预设删除 | 确认后删除                     |

**预设数据结构**：完整保存 `selectedModels` + `selectedLoras` + `params` + `prompt`。

### 3.7 M6 · 提示词助手

**职责**：为每个架构提供国漫向提示词模板。

**功能点**：

| 编号    | 功能    | 说明              |
| ----- | ----- | --------------- |
| M6-F1 | 模板库   | 每个架构一套正/负向模板    |
| M6-F2 | 一键填入  | 生成工作流时自动填入提示词节点 |
| M6-F3 | 用户自定义 | 用户可保存自己的提示词模板   |

**模板示例**：

- Krea2：水墨 / 工笔 / 国风插画 3 套
- MiniMax H3：动作 / 情绪 / 场景 3 套中文模板
- Boogu：写实 / 电影感 2 套

## 4. 非功能需求

### 4.1 性能

| 指标              | 目标          |
| --------------- | ----------- |
| 页面首次加载          | ≤ 1.5s      |
| 模型目录扫描（1000 文件） | ≤ 3s        |
| 兼容性检查           | ≤ 50ms（前端）  |
| 工作流生成           | ≤ 200ms（后端） |
| Patch 校验        | ≤ 500ms     |

### 4.2 可维护性

- 模块间通过明确的接口交互，无循环依赖
- 新增架构只需修改 `architectures.json` 和 `graph_patterns/*.json`，不改代码
- 新增启发式规则只改 `model_scanner.py` 的 `ARCH_SIGNATURES`

### 4.3 可扩展性

- 支持扩展到 SD WebUI 集成（第二版）
- 支持扩展到更多架构（FLUX、Qwen-Image 等）
- 支持远程 LLM API（未来可选）

### 4.4 可靠性

- 注册表修改是原子的（写临时文件 + rename）
- Patch 校验失败不修改注册表
- 扫描失败不影响页面其他功能

### 4.5 可观测性

- 所有 LLM Patch 保留历史记录（`data/patches/` 目录）
- 每次扫描记录耗时
- 校验失败返回结构化错误

## 5. 数据模型

### 5.1 注册表（`model_registry.json`）

```
{
  version: string           # 版本号，Patch 必须匹配
  lastUpdated: ISO8601
  architectures: {}          # 引用 architectures.json
  models: ModelEntry[]
  compatibilityMatrix: {}    # 引用 architectures.json
}

ModelEntry:
  file: string              # 文件名
  dir: string               # 一级目录
  arch: string | null       # 架构 ID
  role: enum                # unet/encoder/vae/.../unknown
  source: enum              # metadata/heuristic/llm_patch/initial
  confidence: float         # 0.0~1.0
  needs_llm: boolean        # 是否需要 LLM 补全
  signals: string[]         # 推断依据
  metadata: {}              # safetensors 头部提取的原始信息
  
  # 架构相关
  compatibleEncoders: string[]
  compatibleVaes: string[]
  compatibleLoras: string[]
  encoderNodeParams: {}
  
  # LoRA 相关
  triggerWord: string
  defaultWeight: float
  
  # 参数
  defaultParams: {}
```

### 5.2 架构定义（`architectures.json`）

```
{
  architectures:
    <arch_id>:
      label: string
      unetFolder: string
      encoders: string[]
      encoderNode: string          # CLIPLoader / DualCLIPLoader / ...
      encoderNodeParams: {}
      vae: string | string[]
      defaultParams: {}
      loraCompatibility: string
  
  compatibilityMatrix:
    <arch_id>:
      compatibleLoras: string[]
      incompatibleLoras: string[]
}
```

### 5.3 图谱模式（`graph_patterns/<arch>.json`）

```
{
  id: string                       # 架构 ID
  nodes: [
    {
      key: string                  # 内部引用键
      type: string                 # ComfyUI 节点类型
      widgets: string[]            # widget 名称列表
      widgetsDefaults: any[]       # widget 默认值
      pos: [x, y]
      size: [w, h]
    }
  ]
  connections: [
    [sourceKey, sourceSlot, targetKey, targetSlot, type]
  ]
  loraInsertion:
    from: string                   # 源节点 key
    to: string                     # 目标节点 key
    targetSlot: int
    nodePos: [x, y]
    nodeSize: [w, h]
  optionalNodes: [
    {
      key: string
      type: string
      optional: string             # firstFrame / lastFrame / ...
      targetKey: string
      targetSlot: int
    }
  ]
  modelInjections: [
    { key: string, widgetIndex: int, modelKey: string }  # modelKey: unet/encoder/vae/...
  ]
  paramInjections: [
    { key: string, widgetIndex: int, param: string }
  ]
  promptInjections: [
    { key: string, widgetIndex: int, role: string }      # positive / videoPrompt
  ]
}
```

### 5.4 预设（`presets.json`）

```
{
  presets: [
    {
      id: string
      name: string
      createdAt: ISO8601
      ecosystemId: string
      models: {}
      loras: [{ name, weight }]
      params: {}
      prompt: string
    }
  ]
}
```

### 5.5 Patch 历史（`data/patches/<timestamp>.json`）

每次成功合并的 Patch 保留一份副本，用于审计和回滚。

## 6. 关键技术决策

### D1：为什么不用模板填充

**问题**：模板填充只能生成已知组合，无法探索新组合。

**方案**：图谱模式（Graph Pattern）——描述"这种架构的节点图长什么样"，与具体工作流文件解耦。

**收益**：新增架构只需写一个图谱模式文件，不改代码。

### D2：为什么不用 LLM 做实时推断

**问题**：本地 LLM 占用几 GB 显存，且响应慢（每次几秒）。

**方案**：三层识别 + LLM Patch 兜底。LLM 只在用户主动点「更新模型库」时介入。

**收益**：正常使用零 LLM 开销，只有在新增模型时才走 LLM。

### D3：为什么注册表和扫描结果分离

**问题**：扫描结果是原始信息（文件名、tensor 名称），注册表是加工后的元数据。二者生命周期不同：扫描结果可随时重新生成，注册表是累积资产。

**方案**：

- `scan_cache`：缓存扫描结果，可随时失效
- `model_registry.json`：持久化，Patch 增量更新

**收益**：扫描速度快（可缓存），注册表稳定（不受文件移动影响，只要 file+dir 一致）。

### D4：为什么 Patch 采用字段级合并

**问题**：整体覆盖会导致 LLM 错误推断覆盖已验证信息。

**方案**：

- `source=heuristic` 的条目：Patch 可覆盖（因为本身不可靠）
- `source=metadata/initial` 的条目：Patch 只能填充缺失字段

**收益**：可靠信息永不被 LLM 错误覆盖。

### D5：为什么选 http.server 而非 FastAPI

**问题**：现有项目（`comfyui-server.py`）已基于标准库 `http.server`，引入 FastAPI 会带来额外依赖和启动开销。

**方案**：保持 `http.server` + 模块化路由。

**收益**：零第三方依赖，内存占用 15-25 MB。

### D6：为什么前端用 vanilla JS

**问题**：引入 React/Vue 会增加构建步骤和运行时依赖。

**方案**：纯 vanilla JS + 集中式 `state` 对象，配合模块化渲染函数。

**收益**：单 HTML 文件可加载，无构建流程。

## 8. 风险与缓解

| 风险                     | 影响        | 缓解措施                           |
| ---------------------- | --------- | ------------------------------ |
| Layer 1b 启发式误判         | 生成的组合不可用  | 标记 source=heuristic，UI 显式提示置信度 |
| LLM Patch 质量参差         | 注册表污染     | 严格校验 + 保留 Patch 历史 + 支持回滚      |
| 图谱模式与 ComfyUI 节点实际行为不符 | 生成的工作流跑不通 | 每个图谱模式必须经过一次实际运行验证             |
| 用户目录改动导致 file 失效       | 注册表有孤儿条目  | 提供「清理未找到文件」操作                  |
| 架构 ID 命名冲突             | 扩展性差      | 架构 ID 使用小写蛇形命名，避免缩写            |

## 2. 分层设计

| 层                     | 职责                  | 依赖方向   |
| --------------------- | ------------------- | ------ |
| **路由层** (`routes/`)   | HTTP 请求分发、参数解析、响应封装 | ↓ 服务层  |
| **服务层** (`services/`) | 业务逻辑、领域模型、算法        | ↓ 存储层  |
| **存储层** (`storage/`)  | 持久化读写、缓存管理          | ↓ 文件系统 |
| **数据层** (`data/`)     | 静态配置、动态数据           | —      |

**关键约束**：路由层不直接操作存储，必须通过服务层；服务层不知道 HTTP 的存在。

## 3. 模块依赖

```
routes/
  ├── registry_routes  ──→ services.ModelRegistry, services.ModelScanner,
  │                         services.PatchValidator, services.PromptBuilder
  ├── workflow_routes  ──→ services.CompatibilityEngine, services.GraphBuilder,
  │                         services.WorkflowSerializer
  └── preset_routes    ──→ storage.PresetStore

services/
  ├── ModelRegistry    ──→ storage.RegistryStore
  ├── ModelScanner     ──→ (无依赖，纯函数)
  ├── PatchValidator   ──→ (无依赖，纯函数)
  ├── PromptBuilder    ──→ (无依赖，纯函数)
  ├── CompatibilityEngine ──→ services.ModelRegistry
  ├── GraphBuilder     ──→ services.ModelRegistry, storage.GraphPatternStore
  └── WorkflowSerializer ──→ (无依赖)

storage/
  ├── RegistryStore    ──→ 文件系统
  ├── PresetStore      ──→ 文件系统
  ├── GraphPatternStore ──→ 文件系统
  └── CacheStore       ──→ 文件系统
```

**无循环依赖**。`CompatibilityEngine` 和 `GraphBuilder` 是唯二依赖 `ModelRegistry` 的模块。

## 4. 数据流

### 4.1 模型扫描流程

```
用户点击「重新扫描」
  → routes.registry_routes.handle_get("/api/registry/scan")
    → services.ModelScanner.scan_models_dir()
      → 对每个文件执行 Layer 1a + Layer 1b
      → 返回 List[ModelEntry]
    → storage.CacheStore.save_scan_cache()
    → services.ModelRegistry.get_unregistered()
    → 返回 { scannedCount, unregisteredCount, models }
  → 前端渲染分类列表
```

### 4.2 Patch 更新流程

```
用户点击「复制更新提示词」
  → routes.registry_routes.handle_get("/api/registry/update-prompt")
    → services.ModelRegistry.load()
    → services.ModelScanner.get_cached_scan()
    → services.PromptBuilder.build_update_prompt()
    → 返回 { prompt, targetCount }
  → 前端复制到剪贴板 → 用户粘贴给 LLM

用户上传 Patch
  → routes.registry_routes.handle_post("/api/registry/patch")
    → services.PatchValidator.validate_patch()
      → 校验版本、文件存在性、字段合法性
      → 返回 { valid, issues, normalized_patch }
    → 如果 valid:
      → services.ModelRegistry.merge_patch()
      → storage.RegistryStore.save()
      → storage.PatchHistory.save()
      → 返回 { added, updated, total }
    → 如果 invalid:
      → 返回 { errors, warnings }
  → 前端展示结果或错误
```

### 4.3 工作流生成流程

```
用户在 Tab 2 勾选模型
  → 前端实时调用 services.CompatibilityEngine（后端）
    → 返回 { compatible, missing, conflicts, recommendations }
  → 前端渲染兼容性报告

用户点击「生成工作流」
  → routes.workflow_routes.handle_post("/api/workflow/generate")
    → services.CompatibilityEngine.check() 二次校验
    → services.GraphBuilder.build()
      → 根据 ecosystemId 加载 graph_patterns/<id>.json
      → 实例化节点
      → 注入模型文件名
      → 插入 LoRA 节点
      → 注入参数
      → 注入提示词
    → services.WorkflowSerializer.serialize()
      → 构建 links 数组
      → 分配 last_node_id / last_link_id
      → 输出最终 JSON
    → 返回 { workflow, pluginDependencies }
  → 前端预览 / 下载 / 保存
```

## 6. 扩展点

### 6.1 新增架构

只需两步：

1. 在 `architectures.json` 中添加架构定义
2. 在 `graph_patterns/` 下添加对应的图谱模式 JSON

无需修改任何 Python 代码。

### 6.2 新增启发式规则

在 `model_scanner.py` 的 `ARCH_SIGNATURES` 字典中添加新规则。规则格式：`(正则表达式, 权重)`。

### 6.3 新增工作流能力

如果未来需要支持"图生图"、"ControlNet"、"多 LoRA 串联"等能力，在图谱模式的 `optionalNodes` 中扩展。生成器无需修改。

### 6.4 未来接入 SD WebUI

如果未来需要支持 SD WebUI：

1. 新增 `webui_routes.py`
2. 在 `graph_patterns/` 中添加 SD WebUI 对应的工作流模式（不同的 JSON 格式）
3. 前端增加 Tab 切换

架构不变。

## 7. 部署与运行

### 7.1 运行时依赖

- Python 3.10+（标准库）
- 无第三方依赖
- 内存占用 ≤ 50 MB
- 启动时间 ≤ 1 秒

### 7.2 启动方式

用户双击 `comfyui-server.py`，脚本自动：

1. 加载 `data/` 下的所有配置
2. 启动 HTTP 服务（默认端口 17890）
3. 打开浏览器到 `http://localhost:17890`

### 7.3 数据备份

用户只需备份 `data/` 目录，即可保存所有注册表、预设、图谱模式。
